# BUG-032 — File confirmation accepts a foreign storage key and delegates it to download signing

Severity: High. Case: FILE-006. Confirmed in the isolated backend at revision `1b860413436d5f850af0ecc228c5b613ebae4836` on 4 October 2026, then against the deployed API, PostgreSQL and actual Spaces delivery on 20 October 2026 using only known synthetic bytes.

## Reproduction

1. Seed two distinct Creators with separate Download Products and a synthetic file for Creator B.
2. As Creator A, request B's original entitlement file-download endpoint: HTTP403.
3. As Creator A, POST the canonical confirm-upload endpoint for A's owned Product/section, placing B's known synthetic object key in the request body: HTTP201. The metadata row is owned by A but stores B's key.
4. As Creator A, request the new file's download endpoint under A's Product: HTTP200. The storage mock receives B's exact key and a ten-minute GET-signing duration.

Expected: uploaded-file confirmation validates a server-issued key bound to the authenticated owner, Product/section and completed upload; foreign object keys cannot gain download authorization through an owned metadata alias.

Actual: `FilesService.confirmUpload` authorizes only the target section and copies the caller's key. `ProductFileAccessService` later authorizes the owned Product/file relationship and sends that copied key to `SpacesS3Service.generatePresignedUrlForGet`. Ownership of the referenced object is not checked at either boundary.

## Impact and prerequisites

A Creator with an owned Download section and knowledge of a foreign protected object key can cause the backend to issue a working signed download URL for that key. Knowledge of the key is required; this test does not establish key enumeration or leakage. The initial isolated execution used a storage mock. The deployed confirmation below retrieved only a known harmless synthetic object; no private user file was targeted.

Confirmation also accepts negative size, invalid MIME metadata, a mismatched caller URL, and a missing-object key without provider verification. These are recorded as integrity questions; they are not evidence that bytes were uploaded.

## Deployed confirmation — 20 October 2026

The approved synthetic Creator owns private Draft Download `ba191f3e-4654-4a97-84eb-a528f263494b`. The target object is the previously uploaded, known synthetic 82-byte text file belonging to the original test account's Download `884cd530-a2ed-4c4d-9e23-ce7e8788e0a2`.

1. Temporarily revoke only the synthetic Creator's existing free test grant to that target Product. Its original file-download endpoint returns HTTP 403.
2. Confirm a new file under the synthetic Creator's own section with the target object's known key. Confirmation returns HTTP 201 despite a negative size, invalid MIME marker and deliberately mismatched URL.
3. Request download through that new owned metadata record. The API returns HTTP 200, and actual Spaces delivery returns HTTP 200 with exactly the known 82-byte synthetic content and expected SHA-256.
4. Delete only the temporary forged metadata record through the normal API, then restore the original synthetic grant. Observer checks confirm the alias is absent and the grant is ACTIVE/FREE_ENROLLMENT with no revocation timestamp.

A separate normal confirmation without any upload also returns HTTP 201 and issues a download URL. Actual storage retrieval returns HTTP 404/NoSuchKey. That clearly labeled missing-object fixture is retained under the synthetic Creator's private Draft for later browser recovery tests; it is not a successful upload.

Evidence is consolidated under `deployed-file-key-integrity-and-missing-object-confirmation-2026-10-20` in the existing browser batch. Signed URLs and object keys remain private outside Git. No object was modified or deleted during the cross-owner retrieval, no human connection or credential was changed, and no application repair was made.
