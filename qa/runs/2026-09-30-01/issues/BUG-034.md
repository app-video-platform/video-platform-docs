# BUG-034 — Contact agreement still looks checked after toggling off

- Severity: Medium — visible agreement state contradicts the native checkbox.
- Status: Confirmed in the current isolated frontend browser; deployed reproduction pending.
- Case: MKT-010.
- Roles: Guest and synthetic User, Creator and Admin.
- Observed: 4 October 2026.
- Frontend revision: `12765d4568796f8472124383a221b74d82850c5b`. Deployed revision unknown.

## Expected

Turning the agreement checkbox off removes the visible tick and keeps the displayed state consistent with the native input. The control can be reached and operated with a keyboard.

## Actual

The fresh control is unchecked both visually and natively. Clicking its label turns both on. Clicking again sets native `checked=false`, but the label retains its `checked` class and the visible tick remains. This reproduces under all four synthetic role fixtures with otherwise valid contact fields.

The input has `display:none` and is absent from the accessible checkbox inventory. Tab from Message moves directly to Beam it Up, skipping the agreement control. The default DOM `tabIndex=0` does not make a hidden input focusable.

Initial unchecked, checked, and unchecked-after-toggle submissions keep the same form and generate no contact API request. The checkbox is not required by native form validation. Whether agreement should gate a future submission is unspecified; no consent enforcement or message delivery is claimed.

## Reproduction

1. Open `/contact` in the current frontend build with synthetic form data and all outgoing API mutations blocked.
2. Fill First Name, Last Name, Email, Topic and Message with valid fictional values.
3. Click the agreement label once, then again.
4. Observe that the visible tick remains while the native input is unchecked.
5. Focus Message and press Tab. Focus moves to Beam it Up.

## Implementation and scope

`ContactForm.handleChange` reads `event.target.value` for every field, including the checkbox, instead of its boolean `checked`. `CheckboxInput` consumes the `checked` prop only for its label class and does not pass it to the native input. The stylesheet hides that input. These current sources support the observed visual/native mismatch and keyboard skip.

The real app router and components were exercised in Chrome through a temporary localhost frontend build. Role/profile responses are synthetic, and API mutations, external fetch and off-origin resources are blocked. No deployed account, real contact message, legal agreement or backend record was changed.
