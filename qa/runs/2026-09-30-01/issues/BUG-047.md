# BUG-047 — Homepage animation styles prevent sibling card dimming

- Severity: Low
- Case: MKT-017 / deployed Guest sibling opacity
- Status: Confirmed; no application change
- Environment: deployed homepage, independent Guest browser with observed scroll animations. Deployment revision unknown.

## Reproduction

1. Scroll to the homepage's trust cards and allow their reveal animation to finish.
2. Point at Secure Checkout.
3. Compare the active card and its three siblings.

Expected: the deployed `.trust-card.is-dimmed` CSS opacity of `0.42` applies to the siblings. Product and feature dimmed selectors similarly specify `0.38`.

Actual: the active/dimmed classes change correctly, but every trust card retains computed opacity `1`. The siblings have inline `opacity: 1` from the animation, overriding the dimmed class rule. Their saturation change still applies; the failure concerns opacity specifically.

The three Product cards and five feature buttons likewise retain computed opacity `1` when their sibling classes are dimmed. The deployed stylesheet rules were read directly; the trust-card inline conflict was confirmed after viewport reset and revisit.

[Marketing browser batch](../evidence/signed-in-marketing-batch-2026-10-02.json), entry `deployed-guest-home-animation-keyboard-2026-10-08`: pointer/focus state snapshots, computed opacity, deployed CSS rules and `trust-revisit-inline-dim-conflict` inline styles. Temporary screenshot `/private/tmp/vpqa-guest-trust-dim-conflict-2026-10-08.png` shows the trust cards after selecting the first card.

Current animation code ends at full opacity and clears only `willChange`, consistent with this conflict. Source identity of the deployment, signed-in roles and reduced-motion behavior remain unverified. This does not imply that all highlight effects fail.

No account, Product, payment or provider mutation. Temporary Guest tabs closed and viewport override reset.
