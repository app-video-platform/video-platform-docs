# BUG-071 — Older Customer response overwrites the selected profile

- Severity: Medium — wrong Customer identity and business details under the current route.
- Status: Confirmed with current frontend source and controlled read-only responses; not fixed.
- Case: CUSTOM-010.
- Environment: isolated actual App/router/store with synthetic Creator profile and two sanitized Customers. No deployed latency reproduction or foreign-access claim.

## Reproduction

1. Open Customer B and let it finish loading.
2. Switch to Customer A while its detail GET is delayed.
3. Switch back to B; let the newer B response finish first.
4. Release the older A response.

## Expected

Only the response for the current Customer route updates the profile. While a different target loads, the old profile is not presented as the newly selected Customer.

## Actual

The older A response replaces the heading, email and summary with A while the URL still points to B. The wrong profile persists after both requests complete. A normal reload at B restores B. A simple A→delayed B switch also keeps A visible without a loading marker until B resolves.

## Cause and evidence

`customers.slice.ts` accepts every detail fulfillment without checking the current Customer/request identity. Pending retains `currentCustomer`. `customer-detail.component.tsx` displays loading only when there is no stored Customer, and does not compare that Customer ID to the route ID.

The consolidated packet `isolated-customer-detail-stale-response-completion-2026-10-24` retains DOM/route snapshots, ordered GET response timestamps, sanitized fixture transport and current source snapshots/hashes. The newer B response completed at 08:59:55.341Z; the older A response completed at 08:59:55.661Z. No real Customer data, grants, account roles or application implementation were changed.
