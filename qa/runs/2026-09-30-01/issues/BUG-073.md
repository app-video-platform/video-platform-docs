# BUG-073 — Protected pages render after logout when authentication is null

- Severity: Medium — client navigation continues to mount protected pages after logout.
- Status: Confirmed in an isolated browser running the unchanged frontend; not fixed.
- Case: NAV-008.
- Environment: actual App, router, Redux reducers, API client and account-menu logout handler, with declared synthetic profile responses and controlled local logout responses. No cloud account, role or authentication configuration changed.

## Reproduction

1. Open protected Settings with a successful synthetic User, Creator or Admin profile response.
2. Use the normal account menu's Logout action.
3. While the logout response is pending, observe that authentication is `null`, loading is false, and Settings remains mounted.
4. Complete the logout response successfully. The normal handler navigates to the marketing home.
5. Use browser Back. Settings renders again with `user=null` and `isUserLoggedIn=null`, rather than redirecting to sign-in.

The same null state also mounts `/app/admin` and its three management tiles. In a control run, a confirmed User profile is correctly redirected from that route to `/unauthorized`; clearing authentication to null then permits the Admin landing page to render.

## Expected

After logout, protected pages require a confirmed authenticated user. Back navigation and in-app navigation must not treat null authentication as permission to mount protected children. A pending profile request may show the existing spinner.

## Actual

User, Creator and Admin normal logout flows all leave null authentication. Protected Settings can be reopened through browser history. The Admin landing page also renders in the null state. By comparison, a failed initial profile request sets authentication to false and correctly redirects to sign-in for all four role fixtures.

A full reload followed by a failed profile response restores the sign-in redirect. This limits the demonstrated defect to frontend state and navigation handling.

## Implementation and evidence

`ProtectedRoute` redirects only when `isUserLoggedIn === false`. Its role check runs only when that value is truthy. With null authentication and no loading, it returns its children. Both the local logout reducer and fulfilled logout thunk set authentication to null. `AppInitializer` refetches on mounting, not on every subsequent route change.

Consolidated evidence packet `isolated-auth-loading-failure-null-logout-route-completion-2026-10-25` contains role-specific DOM observations, the displayed instrumentation state, HTTP request timing and source snapshots. The controlled transport observed only profile GETs and logout POSTs; no Admin user, Product or audit data was requested.

This does **not** demonstrate backend authorization bypass, access to real Admin data, or a deployed latency reproduction. The defect is distinct from BUG-058's retained reporting data across account changes. Application source remains unchanged.
