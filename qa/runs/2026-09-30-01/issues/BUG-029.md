# BUG-029 — Profile validation permits text that does not fit persisted columns

- Severity: Medium — supported profile input is rejected at persistence time.
- Status: Confirmed in the current backend with isolated API fixtures using the deployed column widths; deployed API/browser reproduction remains pending.
- Case: PROF-013.
- Roles: synthetic User, Creator and Admin.
- Observed: 3 October 2026.
- Backend revision: `1b860413436d5f850af0ecc228c5b613ebae4836`. Deployed revision unknown.

## Expected

Values within the profile DTO limits can be saved. Values exceeding the supported limits receive field validation errors without a partial save. API validation and database capacity agree.

## Actual

| Field | DTO limit | Confirmed deployed column limit | Isolated API result at DTO limit |
| --- | ---: | ---: | --- |
| Bio | 1,000 | 500 | 400, database length rejection |
| Tagline | 500 | 250 | 400, database length rejection |
| Website | 255 | 100 | 400, database length rejection |

All three failures reproduce for User, Creator and Admin: nine rejected at-limit saves. They pass DTO validation, have no corresponding field-error entry, and fail against the narrower database column. The existing profile remains unchanged.

Oversized values and malformed public email receive normal field validation errors. Other tested at-limit fields save successfully, including the 320-character email fixture accepted by the current validator. These controls distinguish the persistence mismatch from a general profile or authentication failure.

## Reproduction

1. Start the current backend with disposable local data, real security filters, and mocked external services.
2. Give the isolated `users` fields the widths confirmed by the restricted read-only schema query. This reproduces the repository's profile migration widths; no deployed schema is modified.
3. Authenticate a synthetic User, Creator or Admin and supply a matching CSRF pair.
4. PUT `/api/user/userInfo` separately with Bio of 1,000 characters, Tagline of 500, and Website of 255.
5. Observe HTTP 400 from persistence and verify the original profile remains unchanged. Repeat with an oversized value to compare the normal field-validation response.

## Scope

The read-only deployed database query verified column names, types and lengths only. It read no account rows and changed no data. The rejected PUT requests ran against the isolated backend with H2 columns matching those verified capacities. No rejected save was attempted on the real account, and the deployed API version is unknown.

`UpdateUserRequest` defines the larger validation limits. Migration `18-add-users-details.sql` defines the narrower Bio, Tagline and Website columns; the deployed metadata matches those widths. Hibernate-generated test columns alone do not represent these migration constraints, so the fixture makes this distinction explicit.
