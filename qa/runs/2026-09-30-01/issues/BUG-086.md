# BUG-086 — Profile-service outage redirects an existing session to Sign in without explanation

- Severity: Medium.
- Status: Confirmed in current-source isolated browser integration; not fixed.
- Related case: ENV-010.
- Environment: actual frontend App and Java17 backend/PostgreSQL15.19 with all40 migrations, loopback response-interruption proxy,29October2026.

## Reproduction and result

An enabled synthetic Creator has a normal backend login and a working Product list. The browser fixture declares that existing authenticated frontend state; the local proxy attaches the normal synthetic backend session to protected API reads. Public Storefront requests are sent without that session.

When all API reads return controlled503, opening the private Product route redirects to `/auth/login`. The page shows Email, Password and Sign in, with no backend-unavailable explanation. The public Storefront correctly shows its unavailable state for the same outage.

When the profile request remains200 but Product data returns503, the Product route instead shows `Products could not load`, the unavailable message and Retry. Retry while unavailable retains the error. After access is restored, Retry and full reload render the same Product again. The public Storefront also recovers after reload.

`AppInitializer` dispatches the profile read, and the auth slice sets `isUserLoggedIn=false` for every rejected profile fetch, including503. The private-route guard then presents Sign in. This observation does not establish actual cookie deletion or backend credential revocation; it confirms misleading frontend treatment of an availability failure as loss of authentication.

## Scope and evidence

Consolidated packet `isolated-real-backend-public-private-outage-and-recovery-2026-10-29` retains browser states, sanitized GET-only proxy trace, setup/final database counts and source snapshots. Existing-session bootstrap and proxy credential attachment are declared instrumentation, so this is not normal browser sign-in, cross-device session persistence or deployed-cloud outage evidence.

No cloud service was interrupted. All temporary services and the browser tab are closed. No app fix or data-changing browser request was made.
