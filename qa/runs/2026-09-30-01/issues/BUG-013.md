# BUG-013 — Search pagination hides available later results

- Severity: Medium
- Status: Confirmed; not fixed in this test execution pass
- Related cases: DISC-009, DISC-011 and DISC-012
- Role: Guest
- Environment: deployed frontend and anonymous public API

## Reproduction

1. Direct-load `/app/explore/search?term=` with the existing catalog containing more than20 Products.
2. Inspect the first20 results and Next.
3. Compare public search responses for `page=0` and `page=1`, with the same empty term and size20.

## Expected

Pagination reports the complete matching result count consistently across pages, enabling Next while later matching results exist.

## Actual

The browser disables Next on the first20 results and displays `Page0of1`. The public API reports:

| Requested page | Returned rows | totalElements | totalPages | last |
| --- | --- | --- | --- | --- |
| 0 | 20 | 20 | 1 | true |
| 1 | 20 | 40 | 2 | true |

Page1 contains additional results despite page0 claiming to be the last page. Users cannot reach those additional results through Next.

The first-page label also uses0, rather than the later-page display convention. This wording issue is secondary to the inaccessible later results.

## Isolated owner-search confirmation — 4 October 2026

The current backend owner-search route reproduces the same pagination failure with disposable H2 fixtures. Each of two Creators owns twelve matching Products across four types and three states. Guest, User, Creator and Admin each query both owners with name ascending, name descending and creation-date descending requests.

With size five, page zero reports five total results and one page; page one reports ten total results and two pages. Both incorrectly say `last=true`. Page two returns the remaining two matches and reports twelve results and three pages. All 24 role/owner/sort combinations reproduce; owner isolation, actual title sorting and returned identity/status fields pass independently.

The exact catalog page-zero/size-twenty control correctly returns all twelve matches for each of eight role/owner combinations. The defect appears when enough matches require multiple pages. The synthetic Published Membership rows are legacy read-model fixtures, not successful Membership publication.

[Existing Product API evidence batch](../evidence/backend-product-ownership-publication-batch-2026-10-03.json), key `isolated-admin-gates-owner-search-consultation-details-matrix`, retains the precise sources, pagination metadata, successful controls and cleanup. This extends the existing issue; no new defect or fix. It does not prove the owner-specific route was exercised on the deployed database or in the browser.
