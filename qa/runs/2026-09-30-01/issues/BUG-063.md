# BUG-063 — A calendar with no token expiry breaks the entire connection list

- Severity: Medium.
- Status: Confirmed; not fixed in this testing pass.
- Related case: CAL-011.
- Environment: deployed backend and PostgreSQL, 20 October 2026.
- Actor: approved synthetic Creator `bdd18a60-df1b-45c6-819c-911ff72700e5`.

## Reproduction

1. Prepare isolated calendar connection records owned by a synthetic Creator. Use noncredential placeholder token fields; do not connect a real provider account.
2. Give all records a non-null expiry and request `GET /api/calendars`: the list returns HTTP 200.
3. Set one record's nullable `expires_at` to null and repeat the request.
4. Restore that expiry and repeat the request.

## Expected and actual

The schema permits a missing expiry, and the callback service explicitly permits a token bundle without one. Listing should handle that supported persisted state without inventing an expiry or losing the other connections.

Instead, a single null expiry causes HTTP 400 for the whole list. The response identifies a null `toInstant()` conversion. The other two connections cannot be listed either. Restoring only the expiry immediately restores HTTP 200 and all three records.

The deployed test reproduced independently with Google, Microsoft and iCloud records. The iCloud row is a persistence fixture, not evidence that iCloud OAuth connection works.

## Source and limits

`CalendarIntegrationService.listMyCalendars()` calls `c.getExpiresAt().toInstant()` without a null guard. `handleOAuthCallback()` sets expiry only when the provider supplies it, and its response directly accepts the nullable value. The entity and database allow null expiry.

These tests exercise the real deployed list and recovery paths. They do not prove that a real provider callback produced a null expiry; that callback variation remains unexecuted, and CAL-011 remains partially assessed.

## Evidence and cleanup

Existing consolidated browser batch key `deployed-calendar-null-expiry-isolated-owner-2026-10-20` contains the sanitized response matrix, fixture IDs, source hashes and cleanup result. No provider credentials or authorization codes were used.

All three temporary records were removed by exact fixture ID and synthetic owner. The Creator's calendar list returned HTTP 200 with zero connections afterward. Existing human connections were untouched.

## Consultation read also fails — 20 October 2026

The same nullable state also breaks canonical Product reads. A new synthetic Creator-owned Draft Consultation, `89f19565-c4cd-42ac-9c3d-0861f760685b`, normally returns its two synthetic calendar summaries. Setting one connection's expiry to null makes `GET /api/products/{id}` return HTTP 400 with a null `toString()` conversion. Restoring only that expiry returns HTTP 200 and both summaries again.

`ConsultationProductConverter.toCalendarDto()` calls `cal.getExpiresAt().toString()` without a null guard. This is a second manifestation of the same nullable-expiry defect; it does not establish that every Product type or public search route fails.

Both owned calendars were then removed through the normal authenticated DELETE endpoint. Fresh calendar and Consultation reads reflected the remaining connection after the first removal and an empty list after the second. An unrelated synthetic connection used for ownership rejection was removed separately by exact ID and owner. No real provider credentials were used. Evidence key: `deployed-calendar-own-disconnect-and-product-null-expiry-2026-10-20` in the existing consolidated batch.
