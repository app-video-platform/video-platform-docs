# BUG-062 — Inputs styled as disabled remain in keyboard navigation

- Severity: Low — disabled fields are presented as interactive inputs to keyboard and accessibility users.
- Cases: UX-016 and PROF-005.
- Scope: deployed Creator, Admin and User Settings Profile on 20 October 2026.

## Reproduction

1. Open Settings Profile.
2. Focus Last Name and press Tab. Focus moves to the login-email input styled as disabled.
3. Focus Website and press Tab. Focus moves to the Facebook prefix input styled as disabled.
4. Inspect the focused input's native properties.

Expected: inputs declared disabled are disabled natively and skipped by Tab navigation. Actual: both inputs receive keyboard focus with class `input-field disabled`, `disabled=false`, `readOnly=false` and `tabIndex=0`. The social prefix visibly receives the focus outline and text selection. All three roles reproduce the behavior.

## Cause and limits

The shared `Input` component destructures `disabled` and `readOnly` and uses them as CSS classes, but does not pass either property to the rendered input. Settings supplies `disabled` for the login-email field and social prefixes.

These Settings fields use controlled values with no-op change handlers. No login-email change, credential change or server mutation was attempted or demonstrated. This is a native input semantics and keyboard-navigation defect, not evidence of an authentication bypass. Other consumers of the shared component have not been exhaustively tested here.

## Evidence and cleanup

Existing consolidated browser batch key `deployed-profile-local-form-validation-and-fixture-restoration-2026-10-20` retains the per-role focus properties and source hashes. The runtime screenshot shows the Facebook prefix focus without the private login email.
