# BUG-085 — Reverse-geocoding failure throws without visible feedback

- Severity: Medium.
- Status: Confirmed in current-source isolated browser component; not fixed.
- Related case: PROF-017.
- Environment: unmodified OSMLocationSearch and installed autocomplete dependency; declared synthetic fetch responses, 29 October 2026.

## Reproduction

1. Type a synthetic location query and return a successful autocomplete result.
2. Select the result.
3. Return HTTP503 with an error object from the reverse-geocoding dependency.

The input displays the selected location, but the callback remains null. The browser records `TypeError: Cannot read properties of undefined (reading 'city')` in `fetchStructuredAddress`. No visible error explains the failed selection.

The wrapper reads JSON without checking `res.ok`, then dereferences `data.address.city` without an error handler. The error object has no address. Successful synthetic search/reverse responses map city, country, latitude and longitude correctly. A rejected search request instead displays `No locations`, which does not distinguish an outage from no matches.

This proves component error handling for the controlled503 response. It does not prove live Nominatim availability, deployed onboarding persistence or real geolocation permission behavior. No real coordinates or external request were used. The wrapper and dependency expose no observed current-location control; the catalog permission branch remains a separate clarification.

## Evidence

Consolidated packet `isolated-actual-profile-social-and-location-controls-2026-10-29` contains component browser observations, bounded exception details, declared transport fixture and source snapshots. Synthetic controls reset; temporary tab and server closed. No cloud changes.

## Ownership review — 3 November 2026

Frontend-only. Current source in
`video-platform-ui/src/domains/app/components/location-search/location-search.component.tsx`
shows `fetchStructuredAddress` calling Nominatim directly and reading
`data.address.city` before the selection callback. An HTTP 503 error object
therefore fails in the browser before any profile persistence call. The Java
backend has no geocoding handler in this path.

Trello label corrected to Frontend; its workflow column was preserved. The
frontend fix should check HTTP status and response shape, catch request
failures, display a visible retryable error, and avoid submitting an invalid
selection. No frontend or backend implementation change was made for this
issue; the recorded browser reproduction remains open.

## Resolution and verification — 3 November 2026

- **Frontend implementation complete and merged:** M3 [PR #73](https://github.com/app-video-platform/video-platform-ui/pull/73), frontend main merge `05f25db` (implementation `90ab4b3`).
- Implementation: OSMLocationSearch validates coordinate presence/ranges, response success and complete city/country address data before calling onSelect. Reverse lookup failures show an alert and Retry location lookup for valid coordinates; invalid coordinates require another selection. Request IDs reject stale results. Failed/cleared searches do not overwrite a previously accepted location in the form. The profile payload saves city/country, not coordinates.
- Regression coverage in `video-platform-ui`: `src/domains/app/components/location-search/location-search.component.test.tsx` covers successful mapping, non-2xx retry, network/missing-address errors, malformed coordinates and clearing without replacing an accepted selection. Autocomplete search-provider errors remain a separate dependency behavior.
- **Synthetic frontend verification passed:** PR #73 records 689 tests across 108 suites, TypeScript, ESLint (0 errors, 202 existing warnings), production build and whitespace checks. Synthetic browser verification covered completed-profile onboarding redirects only; incomplete-profile flows have automated component/router coverage, not a completed synthetic browser E2E journey.
- **Live-backend E2E verification pending:** full incomplete-profile onboarding in the browser, real profile saves/reloads and deployed Nominatim error/retry behavior remain unverified for this fix. `UpdateUserRequest` includes city and country, not latitude/longitude. No new backend capability is implied.
- **Deployment/final QA confirmation not yet established.** Historical findings above remain unchanged; earlier “not fixed” statements describe their observation dates. This note does not mark the ticket fully resolved or production-verified. Trello remains the operational status board.
