# BUG-038 — Overlapping drawers share titles and break Escape cleanup

- Severity: Medium — an overlapping modal can retain focus outside it and lose its scroll lock.
- Status: Confirmed in a synthetic composition of the actual shared Drawer component; deployed overlapping-title collision confirmed on 21 October 2026.
- Case: UX-005.
- Observed: 4 October 2026. Report finalized from retained evidence on 7 October.

## Expected

Each dialog has a distinct accessible title. Escape closes the top dialog, restores focus to its parent trigger, and retains the page scroll lock while any modal remains open.

## Actual and reproduction

1. In the isolated shared-component fixture, open Parent, then use its Open nested drawer control.
2. Both dialogs use `id="drawer-title"`; the accessible snapshot names both Parent content. The nested dialog's description resolves the parent's title instead of its own visible Nested content title.
3. Focus the nested close control and press Escape.
4. Parent closes while Nested remains open; focus moves to the outside Open parent drawer button and body overflow returns to an empty value.

A fresh control sequence reproduces the same Escape failure. Closing the orphan can also leave hidden body overflow after all dialogs have closed. In a separate fresh positive control, closing the nested header button and then the parent header button restores focus and scroll correctly. Nested Tab/ShiftTab boundary trapping also passes.

## Implementation and limits

Drawer instances each use the same title ID, install their own document key handler, and independently capture/restore body overflow and prior focus. The fixture uses supported component props and actual user keyboard/button actions; application code is unchanged.

This demonstrates a shared-component overlap failure. No current deployed flow with two simultaneous drawers was reproduced, and the report does not claim one. An empty-body drawer always retains an enabled close button, so the true zero-focusable fallback was not fabricated or claimed as executed. Application route/role reachability remains part of the unfinished case.

## Deployed Sales overlap — 21 October 2026

Using only normal browser actions at375px: open the synthetic Sales Order, close it with Escape, open Filters, then use browser Back to restore the Order query. Filters stays open while the Order Drawer loads above it. Both dialogs use `drawer-title`; both resolve the accessible name Filters even though the top visible title is the Order number/Paid. A fresh repeated sequence produces the same collision.

Top ShiftTab/Tab trapping passes. In this deployed history composition, Escape closes only the Order, retains focused Filters and keeps scrolling locked. Closing the top header and then the parent header likewise restores focus and scrolling correctly. The isolated orphaned-child Escape failure above is not claimed to reproduce in this deployed flow.

Evidence packet: `deployed-sales-overlapping-drawer-reachability-2026-10-21` in the existing consolidated browser batch. All dialogs were closed and default viewport restored. No Order or configuration was changed.
