# BUG-042 — Product media uploads send JSON Content-Type

- Severity: High — valid thumbnail, gallery and promo selections cannot satisfy the media upload contract.
- Status: Confirmed with the current frontend in a controlled browser fixture and the current backend against migrated local PostgreSQL. Deployed browser/storage reproduction remains unverified.
- Case: MEDIA-003.
- Observed: 7–8 October 2026.

## Expected

Raw media requests carry the selected image/video MIME type. Valid files can reach storage after validation.

## Actual and reproduction

1. Render the actual `ProductMediaSection`, Uppy uploader, application Axios client and Product API services with disposable synthetic Product metadata on a loopback server.
2. Select a valid 75-byte PNG for Thumbnail and Gallery, and a valid 1689-byte MP4 for Promo video through the real browser file chooser.
3. All three transmitted bodies retain the exact file lengths, but their Content-Type is `application/json`. The controlled server rejects them with400 and the component displays `Request failed with status code 400`.
4. Submit the same raw bytes and header to the actual three backend handlers using a synthetic owner identity, matching CSRF and PostgreSQL with all40 migrations. All three return400 with `Unsupported media type: application/json`; metadata stays unchanged and storage/email mocks have no calls.
5. As a diagnostic positive control, supply the file MIME explicitly in the fixture callback. The same PNG/MP4 selections send `image/png`/`video/mp4` and the local response controls succeed. This control changes only the temporary fixture, not the application.

The shared Axios client sets a JSON default header. `addImageToProductAPI`, `addProductGalleryImageAPI` and `addProductPromoVideoAPI` pass File bodies without overriding it. Backend media validation rejects that declared MIME before invoking storage.
