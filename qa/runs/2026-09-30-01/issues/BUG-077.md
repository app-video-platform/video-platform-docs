# BUG-077 — Membership aggregate failures trigger repeated automatic requests

- Severity: Medium — a failed dependency is repeatedly requested without a stable recovery state.
- Status: Confirmed with the unchanged Product form, Redux and HTTP client against an isolated HTTP fixture; deployed reproduction is not claimed.
- Case: MEM-019.

## Reproduction

1. Open the Membership Product workspace with no aggregate cached.
2. Return HTTP 503 for the Membership aggregate GET while other required reads succeed.
3. Do not click a retry action.

## Expected

A failed load leaves a readable error and a deliberate recovery path, or uses a bounded retry policy with backoff. A failure must not immediately restart the same request indefinitely.

## Actual

Six sequential GET requests returned 503 and the application issued a seventh without user input. The test fixture held the seventh request to bound traffic; that cap is test instrumentation, not application behavior. The Content surface then showed `Loading products...` rather than a stable failure/retry state.

Restoring the held response to 200 recovered the existing Post and feed entry without a mutation. Separate deletion-error controls retained the item after 503, supported normal retry after restoration, and reloaded the empty feed after a successful 204 response.

## Implementation

The Product form aggregate-loading effect depends on `membershipLoading` and dispatches whenever the aggregate is absent and loading is false. Rejection clears loading but leaves the aggregate absent. The effect starts another fetch; it does not inspect the stored Membership error or a retry budget. The observed request sequence agrees with that current-source behavior.
