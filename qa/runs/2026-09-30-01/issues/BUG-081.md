# BUG-081 — Microsoft Calendar Connect fails before consent

- Severity: High.
- Status: Confirmed; not fixed in this testing pass.
- Related case: CAL-003.
- Environment: deployed backend and normal Calendar Settings, 28 October 2026.
- Actor: synthetic Creator `bdd18a60-df1b-45c6-819c-911ff72700e5`.

## Reproduction

1. Sign in as the synthetic Creator and open Settings → Calendar.
2. Select Microsoft and click Connect.
3. Independently submit the normal authenticated, matching-CSRF `POST /api/calendars/connect` with provider `MICROSOFT`.

## Expected and actual

Initialization should return an authorization URL so consent can start. Instead it returns HTTP400: `Invalid character ' ' for QUERY_PARAM in "offline_access Calendars.Read Calendars.ReadWrite"`. No authorization URL is returned and no connection is created. Google initialization returns200 as a control; its URL is not opened.

The actual Settings action remains on Calendar with Microsoft selected and Connect enabled. It presents no alert/status error feedback. The complete synthetic Creator profile and empty calendar list remain unchanged.

## Source and limits

`MicrosoftCalendarClient.buildAuthorizationUrl` supplies the scope containing spaces, then calls `build(true)`, which treats query parameters as already encoded. The required encoding has not happened. `ConnectedCalendarTab.handleCalendarConnect` has a success-only promise handler and no displayed failure state.

This confirms deployed Creator initialization and its browser failure surface. No real provider identity, consent, token exchange or Admin branch is claimed; the original full provider case remains partially assessed. No provider URLs were opened, no tokens exchanged and no real calendar data accessed.

## Backend review handoff — 2 November 2026

Local fix, not committed or deployed. `MicrosoftCalendarClient` previously
called `build(true)` on raw query values, which declares them already encoded
and rejects spaces and reserved delimiters. Consent URL generation now uses
URI-template variables and strict value encoding before expansion. The scope,
configured redirect URI, signed state, client ID and optional login hint
round-trip intact, including literal plus signs, percent escapes, Unicode and
redirect-URL query strings. Null/empty/blank hints remain omitted. No scopes,
provider endpoints, roles, or callback persistence behavior changed.

Regression coverage:

- `MicrosoftCalendarAuthorizationTest`: four cases first failed on the raw
  query values. They now pass independent URI/form-query decoding, exact
  parameter-map equality, provider endpoint checks, secret exclusion, and
  omitted-hint controls. The hint control uses a plain client ID to exercise
  the original scope-space case as well as reserved-value cases.
- `MicrosoftCalendarConnectIntegrationTest`: Creator and Admin initialization
  return 200 with a valid URL. The decoded URL state equals the returned
  state and verifies through the actual state signer for the expected user
  and Microsoft provider; redirect query and tagged hint are preserved.
  Calendar row count is unchanged. User initialization remains 403.
- The API tests use actual controller/service/configuration/state/JPA
  components, mocked current-user lookup and method-level role identities;
  JWT/CSRF filters are disabled in that test context. No provider URL was
  opened and no Microsoft network request was made.

All seven focused checks and the final full backend suite of 183 tests passed,
with zero failures/errors/skips. Docs typecheck/build passed. OpenAPI, backend
context and developer integration guidance describe using the encoded URL
without rebuilding it. No migration is required.

This verifies initiation only. Live identity/consent, mailbox/provider
prerequisites, and real token exchange are not established. The downstream
Microsoft token-response/form defects remain BUG-082 and BUG-083; frontend
error feedback is unchanged. The original end-to-end provider case remains
partial. Trello is in Dev done for review.

[Spring URI encoding guidance](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-uri-building.html)
explains strict encoding of opaque URI-variable values.
