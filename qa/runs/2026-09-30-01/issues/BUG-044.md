# BUG-044 — Registration client settings conflict with backend CSRF requirements

- Severity: High — the current cross-origin registration client is rejected before registration validation.
- Status: Confirmed through current frontend clients and actual backend HTTP/security on a disposable migrated local database. Deployed reproduction remains unverified.
- Cases: SEC-005, AUTH-005.
- Observed: 8 October 2026.

## Expected

Registration requests supply the matching CSRF cookie/header required by the backend. Client URL formatting cannot silently suppress a required header.

## Actual and reproduction

Use separate loopback frontend/API origins, real application clients and backend handlers, a readable synthetic XSRF cookie and explicitly allowed test-only CORS. Keep the registration payload intentionally invalid so no account or mail delivery is created.

1. Call actual `registerUser`. Its `withCredentials: false` omits browser cookies across origins. The canonical client URL still attaches an X-XSRF-TOKEN header, but the corresponding cookie is absent. Backend returns401 before normal request validation.
2. Send the same invalid payload to canonical `api/auth/register` with credentials enabled as a diagnostic control. The cookie/header pair matches and backend returns400 with normal field validation errors.
3. Send it to leading-slash `/api/auth/register` with credentials enabled. The cookie arrives but the CSRF interceptor's exclusion matches and omits the header. Backend returns401 again.

The backend filter excludes login/logout/refresh/Google sign-in from CSRF checking, but does not exclude registration. The frontend registration client disables credentials and its interceptor excludes a slash-prefixed registration URL. These settings cannot satisfy the current backend contract across origins.

The response interceptor also attempts refresh after these401 responses; the synthetic session has no refresh cookie and those attempts return401. Both original registration responses and refresh requests are preserved, so the refresh result is not mistaken for successful registration.

## Controls and scope

Current profile/Product/enrollment/checkout requests attach matching pairs for canonical and leading-slash URLs. Supported mutations succeed; User Product creation is denied by role rules. Admin Product creation succeeds with a Creator target. Removing the XSRF cookie rejects profile writes; restoring it permits retry with persisted exact titles.

The fixture permits only its loopback frontend origin in the temporary backend CORS source. Synthetic JWT/CSRF cookies use local host settings; this is not verification of deployed domains, Secure/SameSite cookie issuance or real sign-up/mail delivery. Actual application source and cloud accounts remain unchanged. The invalid registration requests create no user; all four seeded users remain the only database users.

## Backend review handoff

The local backend provides a credentialed `GET /api/auth/csrf` for guests. It
returns `{"token":"…"}` with `Cache-Control: no-store` and sets the matching
`XSRF-TOKEN` cookie when needed. It reuses an existing cookie value.

The signup client needs to call the bootstrap with credentials, then submit
registration with credentials and the returned value in `X-XSRF-TOKEN`.
The slash-prefixed registration exclusion must not suppress that header.
The frontend integration and browser registration retest remain open.

The backend suite passed 209 tests. Added coverage exercises a guest registering
with the issued cookie and token from the allowed app origin, reusing the cookie,
and rejecting an untrusted origin. Mail submission is mocked in the test.
