# BUG-078 — Deployed raw-media requests stop at 1 MiB below supported limits

- Severity: High — ordinary valid Product images cannot reach the declared upper boundary.
- Status: Confirmed on the current deployed HTTP routes; exact deployment configuration cause remains unverified.
- Case: MEDIA-009; related configured-limit investigation MEDIA-015.

## Reproduction

Using a signed-in synthetic Creator with matching CSRF and raw `Content-Type: image/png`, POST a valid PNG body to the thumbnail endpoint and gallery endpoint of a private synthetic Course. The fixture is a real 64×64 PNG padded after its image data; ffprobe recognizes the image at the exact 10 MiB file size. There is no multipart overhead.

1. 1,048,576-byte body: HTTP 200 on both endpoints.
2. 1,048,577-byte body: HTTP 413 on both endpoints, unchanged canonical Product response.
3. 10,485,760-byte body: HTTP 413 across Creator-owner/Admin, all four Product types and both endpoints (16 checks).

## Expected

The catalog and repository default allow images through 10,485,760 bytes inclusive. `ProductMediaService` defaults `image-max-bytes` to this value and rejects only size greater than the configured maximum; controllers pass the actual Content-Length and MIME type to the service. Deployment request limits should permit the supported raw image range.

## Actual and diagnosis limits

The measured effective public request boundary is 1 MiB. The one-byte-over probes return an HTML 413 response with `Server: nginx`, rather than the media service's normal validation response. A reverse-proxy request limit is the likely cause, but the responsible configuration, resolved backend overrides and exact proxy hop were not inspected or changed. The public threshold is proven; a specific configuration file or setting is not.

Zero-byte and unsupported-MIME requests return400 and retain exact Product JSON and full `product_media` row hashes. Oversized10MiB+1 requests return413 with the same preservation, which proves public rejection but does not exercise the backend maximum guard. Small JPEG/WebP/GIF controls work across all role/type/endpoint cells. Existing saved-editor crash BUG-001 separately prevents native picker validation.

## Scope and cleanup

All operations target four pre-existing synthetic private Drafts. Added gallery controls were removed, leaving the exact original three image IDs and positions0..2. Final thumbnails are tiny GIF fixtures. Roles/profile/browser are restored to Creator; 37 Orders and 93 entitlements are unchanged. No app, proxy or security configuration was changed.

Evidence packet: `deployed-image-size-mime-boundaries-and-one-mib-public-cap-2026-10-27`. Native picker results and accessible image-byte delivery are not claimed.

## Promo uploads — 27 October

All eight Creator-owner/Admin×four-type promo cells accept a fully transmitted1MiBMP4, but reject a valid1MiB+1MP4 and the declared valid100MiBH264 fixture with HTML413. Standard `Expect: 100-continue` receives final rejection before body upload; cURL reports0uploaded bytes for each rejected attempt. This proves an unsuccessful normal upload attempt at the public boundary, not backend maximum-size validation or receipt of the100MiBbody. Zero and unsupported-MIME requests reject400; smallerMP4/WebM replacements persist READY metadata. Every rejected request preserves the exact full Product response and `product_media` row hashes.

The same effective cap therefore affects image and promo routes, below the repository defaults of10MiB images and100MiB promos. Exact proxy setting/resolved backend overrides remain uninspected. Evidence: `deployed-promo-size-mime-validation-and-early-public-cap-2026-10-27`. No configuration fix was made.
