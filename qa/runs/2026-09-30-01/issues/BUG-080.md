# BUG-080 — Email send errors leave registrations that cannot retry

- Severity: Medium — a failed verification-email request can leave the user without a message and unable to retry registration.
- Status: Confirmed in an isolated current-source API/JPA/H2 harness with actual EmailService and mocked SendGrid transport. Deployed provider-failure behavior is not asserted.
- Case: ENV-005.
- Observed: 28 October 2026.
- Backend revision: `1b860413436d5f850af0ecc228c5b613ebae4836`.

## Recovery expectation

A failed verification-email request needs a usable recovery path. Whether to roll back registration, retry mail sending, or support resend is a product decision. The catalog explicitly leaves failure persistence and rollback for investigation; the observed state below is established, while the preferred recovery design needs confirmation.

## Actual

Controlled provider statuses199,300,400,401,429,500 and IOException return registration HTTP400 but leave one disabled User and one valid verification token committed. Login is401. Re-registering the same email returns401 before another provider call, with no duplicate account/token. In the HTTP controls, the SDK response is switched to202 before retry, but mail is not attempted again. The IOException control remains an exception stub; it too is not reinvoked.

The retained token can enable the account when read directly from the isolated database and submitted to verification. That diagnostic is not an ordinary recovery path for a user who did not receive the email. No public resend route is exposed by the inspected Auth controller.

Positive200/202/299 controls register successfully, prepare the expected sender/recipient/link, deny unverified login, consume a manually obtained valid token, then allow normal login/profile access. These controls test current code and payload construction; they do not establish real mailbox delivery.

## Source and reproduction

`AuthService.register` saves User before `VerificationTokenService.createAndSendToken`. That method saves a token before calling `EmailService`. Neither orchestration method wraps that sequence in a transaction. The real EmailService throws on non2xx/IOException, and the real exception handler returns400.

Run the preserved isolated harness with a fresh H2 database, real Spring MVC/security/JPA and actual Auth, token and Email services. Only SendGrid construction/API is mocked. Register a fresh synthetic address with a valid matching CSRF pair and provider rejection; inspect committed rows, restore the HTTP response control, and retry the same address.
