# BUG-082 — Microsoft accepts an empty access token as a connected calendar

- Severity: Medium.
- Status: Confirmed in current-source isolated integration; not fixed.
- Related case: CAL-007.
- Environment: real isolated HTTP Java17 backend/PostgreSQL15.19 with all40 migrations and controlled WebClient transport,28October2026.

## Reproduction and result

With actual authenticated Creator/Admin callbacks, a controlled Microsoft token response contains an empty `access_token`, synthetic nonblank refresh token and expiry3600. Callback returns200, persists one encrypted connection and list returns200 with it. Decrypting the stored value yields exactly the empty string. Google rejects the same empty-access-token control with400/no connection.

`MicrosoftCalendarClient.exchangeCodeForTokens` reads the value without a blank check. `CalendarIntegrationService` encrypts and persists it, and `TokenCrypto` can encrypt an empty string. A malformed token response should not establish a successful connection.

This is current-source isolated HTTP/PostgreSQL evidence with controlled provider transport. It is not a live Microsoft response or consent test. Normal Microsoft init already fails BUG-081, so this downstream control uses explicitly signed synthetic state from the actual state component. Both created rows were disconnected through normal API204, followed by empty list200. No real token or account is involved.

## Evidence

Consolidated packet: `isolated-actual-calendar-provider-errors-form-encoding-and-null-expiry-2026-10-28`. Corrected v2 execution exited0; local HTTP backend and private database cluster are stopped.

## Backend review handoff — 2 November 2026

Local fix, not committed or deployed. `MicrosoftCalendarClient` now requires
a nonblank string `access_token` before returning a token bundle. Missing,
null, blank, or wrongly typed access values throw a controlled
`OAuthTokenExchangeException` before encryption/persistence. JSON decoding
failures are also converted to a sanitized OAuth error. Refresh-token and
expiry handling remain unchanged; a valid response may still omit expiry.
No migration or automatic cleanup of existing connections is included.

### Regression evidence

`MicrosoftCalendarTokenTest` first failed nine invalid-response controls while
its two valid-response controls passed. The callback API regression separately
reproduced the original issue: empty access token returned 200 and persisted
a connection before the guard. After the fix:

- All 11 client cases pass: null/blank/whitespace/numeric/boolean/object/list
  access fields, absent access field, empty response, valid opaque tokens with
  expiry, and valid tokens with unknown expiry.
- All eight `MicrosoftCalendarCallbackIntegrationTest` cases pass against
  isolated PostgreSQL 15 with all 43 Liquibase migrations and Hibernate DDL
  disabled. Creator/Admin empty tokens and other malformed access values
  return 400 with no connection; list remains empty.
- Valid Creator/Admin controls persist encrypted access/refresh tokens, decrypt
  to the original synthetic values, preserve known/unknown expiry, list
  without exposing stored token material, and disconnect through normal
  API 204. Each callback obtains its signed state through actual consent
  initialization, rather than bypassing state validation.

The API context uses real controller/service/state/crypto/JPA code, controlled
WebClient responses, mocked current-user lookup and method-level role
identities. JWT/CSRF filters are disabled there. Only newly synthetic local
users/connections are created and cleaned up. No live Microsoft request,
consent, credential, or cloud database mutation is involved. The isolated
PostgreSQL server was stopped after verification.

OpenAPI, backend context and developer integration guidance describe rejection
of unusable token responses. Docs typecheck/build passed. Token-form encoding
