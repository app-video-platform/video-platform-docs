# BUG-007 — Invalid email verification token displays success

- Severity: Medium — authentication feedback contradicts the server outcome.
- Case: AUTH-008 / guest-invalid-token-false-success
- Deployment versions: unknown
- Role: Guest
- Fixture: unique synthetic invalid token; no real account/token used

## Reproduction

1. Open `/auth/verify-email?token=QA-2026-09-30-01-invalid-token`.
2. Allow the verification request to finish.

Expected: invalid verification link feedback, since the backend rejects the token.

Actual: the page eventually displays “Email verified! You can now log in.” The backend GET `/api/auth/verify` for the same token returns HTTP 400 with `Invalid token!`. The initial loading state also says Invalid verification link, so its initial text cannot establish the settled outcome.

The catalog flagged the rejection handling for investigation. The observed backend rejection establishes that this success message is false. This is not evidence of an authentication bypass or an account actually being verified.

Evidence: [false success](../evidence/invalid-token-success.jpg), [backend rejection](../evidence/invalid-verification-api.json).

Suspected cause: local component uses `.then` on an async thunk dispatch without unwrapping the rejected result. Deployed revision is not verified.

Missing-token control shows Invalid verification link correctly. Expired real-token variation remains pending. No cleanup required.
