# BUG-083 — Microsoft token form serialization corrupts reserved characters

- Severity: Medium.
- Status: Confirmed in current-source isolated integration; not fixed.
- Related case: CAL-003.
- Environment: real isolated HTTP Java17 backend/PostgreSQL15.19 with all40 migrations and controlled WebClient transport,28October2026.

## Reproduction and result

The real Microsoft WebClient request writer serializes a form containing synthetic authorization code, client secret and redirect URI with reserved characters. Independent form decoding does not recover any of those three original values in16controls across Creator/Admin callbacks. Google preserves all three exactly in16matching controls. Only round-trip booleans are retained, not raw forms or token material.

`MicrosoftCalendarClient.exchangeCodeForTokens` manually concatenates `client_id`, scope, code, redirect URI and secret into one string while declaring `application/x-www-form-urlencoded`. Reserved separators and plus characters are not escaped. Google uses `BodyInserters.fromFormData` and passes the comparison.

The request bytes are generated by the actual clients; the transport response is controlled and no provider network request occurs. This confirms request serialization, not real-provider acceptance/rejection. Downstream Microsoft callbacks use a declared valid signed fixture state because normal initialization is independently broken by BUG-081. No cloud credential or configuration is changed.
