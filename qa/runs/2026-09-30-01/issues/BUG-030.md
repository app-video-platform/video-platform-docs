# BUG-030 — Updating an existing Consultation weekday fails to save

- Severity: Medium — availability corrections cannot be saved in one request.
- Status: Confirmed in the isolated backend and deployed Creator browser/PostgreSQL on20October2026.
- Cases: PAPI-026, PAPI-027, PROD-026, CONS-002 and CONS-003.
- Roles: synthetic Creator owner and Admin.
- Observed: 3 October 2026.
- Backend revision: `1b860413436d5f850af0ecc228c5b613ebae4836`. Deployed revision unknown.

## Expected

After a publication rejection, correcting the existing weekday's enabled state or overlapping windows allows the Consultation to save and publish. There is one availability-day record per Product and weekday.

## Actual

The original publication gates work: disabled availability and overlapping ranges return the expected field-keyed 422 response and preserve the saved Product.

Replacing the existing Monday with corrected availability and requesting Published then returns 400 with an availability-day uniqueness error. All eight variants reproduce: Creator/Admin × Draft/Hidden × disabled/overlapping fixtures. The rejected repair rolls back; the previous Product and schedule remain unchanged.

As a control, clearing availability in a separate save and then adding the corrected Monday permits publication. This control demonstrates that the valid schedule itself is accepted. It is not a recommended user workaround because clearing a schedule is a separate persisted change.

On 4 October, PROD-026 also reproduces the failed correction after malformed-time rejection. Forty-eight fixtures cover Creator/Admin × Draft/Hidden × start/end × six malformed strings. The first request returns the expected 400 `HH:mm` normalization error and rolls back simultaneous name, duration, schedule and status changes. Every corrected request then fails with the same weekday uniqueness error and rolls back. Every isolated clear-then-retry control succeeds. These observations extend the existing defect; no new issue is counted.

## Reproduction

1. Run the current backend with disposable data, real security filters and mocked external services.
2. Create an otherwise publishable Draft or Hidden Consultation with Monday availability. Use either disabled Monday or enabled overlapping windows `09:00–11:00` and `10:00–12:00`.
3. Authenticate its Creator owner or an Admin with matching CSRF cookies/header.
4. PATCH `/api/products/{id}` with Published. Verify the expected 422 availability error and unchanged saved state.
5. PATCH the same Product with Published and `details.weeklyAvailability` containing enabled Monday `09:00–12:00`.
6. Observe 400 with an availability-day uniqueness error; GET confirms rollback.
7. In the isolated fixture only, clear weekly availability while retaining Draft/Hidden, then repeat the corrected publication. It succeeds.

## Implementation and scope

`ConsultationProductConverter.applyAvailability` constructs replacement day entities, then clears and repopulates the existing orphan-removal collection. The entity and migration `39-create-consultation-availability.sql` both enforce uniqueness of `(consultation_product_id, weekday)`. The isolated persistence operation attempts to insert the replacement while the original weekday still occupies that key.

The request, constraint error, rollback and successful controls were observed through the current real API/JPA stack using H2 in PostgreSQL mode. Liquibase was disabled in that context; the relevant uniqueness rule comes from the entity and agrees with the migration. This is not a deployed PostgreSQL or browser reproduction, and no live Consultation was changed.
