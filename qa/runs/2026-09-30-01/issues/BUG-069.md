# BUG-069 — Uploaded Product presentation media returns AccessDenied

- Severity: High
- Status: Confirmed; not fixed in this test execution pass
- Related cases: ENV-006, MEDIA-003
- Environment: development backend, Spaces origin/CDN and deployed public Product page
- Fixture: synthetic Download `1a79acf6-71ad-4a36-85b9-33e63136bf84`

## Reproduction

1. As the synthetic Creator, create a disposable Download with one harmless stored text file.
2. Upload a valid 32×32 PNG as thumbnail and gallery image with `Content-Type: image/png`, and a valid one-second silent H.264 MP4 with `Content-Type: video/mp4`, through the normal media APIs.
3. Publish the synthetic Download through the normal API.
4. Read each returned presentation URL through the configured CDN and corresponding origin; open the public Product page.

## Expected

The Published Product's thumbnail, gallery image and promo video can be retrieved and displayed. Protected Download files remain accessible only through authorized signed URLs.

## Actual

All three media uploads return HTTP 200. The database retains three READY rows with the correct MIME types and sizes: two 99-byte PNGs and one 1,837-byte MP4.

All three presentation URLs return HTTP 403 / `AccessDenied` from both CDN and origin. The public page's two image elements complete with natural width/height zero. Its promo video remains unloaded with ready state zero; a keyboard playback attempt does not establish playback or a native video error.

The same fixture's private text file returns HTTP 403 unsigned, but authorized signed retrieval returns HTTP 200 with the exact expected bytes. This is not evidence of a general object-store outage.

## Evidence and limits

The consolidated browser evidence packet `deployed-public-media-cdn-denial-and-natural-cookie-expiry-2026-10-23` contains API responses projected without URLs, origin/CDN statuses, browser measurements, fixture validation and read-only database results.

The exact storage permission or URL configuration cause is not established. No bucket policy, ACL, CDN configuration or application implementation was changed. Correct-MIME API uploads are setup for this delivery test; the separate browser upload Content-Type issue remains BUG-042.

## Cleanup

The new Product was changed from Published to Hidden through the normal API. The database confirms Hidden and all three READY media rows. The harmless fixture is retained for diagnosis. The original three Published synthetic Downloads remain Published. No existing customer content or grant was changed.

## Backend review handoff — 2 November 2026

Local code fix, not committed or deployed. The upload request previously
omitted an object ACL even though Product responses returned permanent public
CDN URLs. Spaces files are private by default. The storage-boundary regression
reproduced the missing `public-read` ACL for thumbnail, gallery and promo
uploads before the fix. This establishes a code defect consistent with the
observed delivery failure; deployed bucket policy and stored object ACLs were
not inspected because Spaces credentials were unavailable.

`SpacesS3Service.uploadPublicProductMedia` now sets object-level `public-read`
and rejects keys outside the canonical owner/Product/presentation namespace.
`ProductMediaService` uses this method for all three presentation kinds.
Protected Download presigned uploads do not request a public ACL. No bucket
ACL or policy changes are part of the fix. Provider upload failure still
prevents READY metadata and thumbnail replacement. No migration is required.

Verification:

- The original three synthetic fixture rows were read through the restored
  read-only database tunnel. Fresh anonymous CDN HEAD requests still returned
  403 for thumbnail, gallery and promo. No cloud row/object/permission changed.
- All 17 focused checks passed: `SpacesS3ServiceTest` checks public ACL, bytes,
  MIME, namespace rejection and protected signing;
  `SpacesS3HttpIntegrationTest` checks the actual SDK HTTP header on loopback
  and its absence on a protected presigned PUT; `ProductMediaServiceTest`
  checks the three upload kinds and storage-failure preservation.
- The loopback receiver tests request serialization, not actual provider ACL
  enforcement or playable media. Live Spaces delivery remains unverified.
- Backend context and developer integration documentation include the
  permission boundary and a targeted repair procedure for existing objects.
  Documentation typecheck and build passed.

### Deployment and existing-object follow-up

The new ACL is applied only to future uploads after deployment. Existing
private presentation objects require a separately reviewed repair of exact
`READY product_media` keys, verified against owner/Product/kind. The developer
integration page shows per-object inspect/repair commands; no repair runs
automatically. Do not apply it to protected Downloads or make the bucket
public. Verify origin/CDN retrieval and real image/video rendering afterward;
inspect policy/cache configuration if access remains denied.

[DigitalOcean object-permission guidance](https://docs.digitalocean.com/products/spaces/how-to/set-file-permissions/)
confirms the private default and object-level public-read option. Product
documentation should reflect the verified deployment when this fix is merged.
