# BUG-059 — Section order error remains after a successful retry

- Severity: Medium — incorrect failure feedback remains after the intended order is saved.
- Case: CONTENT-005, Course and Download reorder recovery.
- Environment: unchanged current frontend `12765d4568796f8472124383a221b74d82850c5b`, actual isolated backend `1b860413436d5f850af0ecc228c5b613ebae4836`, migrated PostgreSQL. No deployed reproduction claimed.

## Reproduction

1. In a functioning newly created Course or Download workspace, prepare three sections/file groups.
2. Fail one section’s position PATCH with the scoped local 503 fixture, then move the third group up. The other position update succeeds.
3. Observe the inline “Could not save section order.” or “Could not save file group order.” message.
4. Disable the fault. Use normal controls to reverse the move and wait for persistence; retry the original move and wait for all immediate and debounced PATCHes to finish.

Expected: after a verified successful retry, the previous failure message clears or is clearly identified as historical.

Actual: the inline failure message remains in both Product types, while the groups show Saved. All eight retry PATCH responses return 200. Actual authorized Product reads and PostgreSQL verification show the intended unique positions1/2/3 and unchanged section/child identities.

The initial failed reorder was measured on16October. The retained forms survived an interruption. On18October the same Creator signed in normally again in a separate tab, then retried from the retained forms with faults disabled. The working forms were not reloaded or rebuilt, so their stale error state remained observable. No expired-session failure is counted as a reorder result.

## Cause and evidence

`CreateProductSections` sets `operationError` when a position update rejects. A new move and its successful position updates never clear that state. The component continues rendering the old error.

[Existing browser batch](../evidence/browser-populated-reporting-batch-2026-10-03.json), key `section-edit-ordering-partial-failure-recovery-2026-10-18`, records the normal UI actions, initial mixed-save state, all retry statuses, API/SQL verification and exact source snapshots.

## Scope and cleanup

The initial separate PATCHes can persist duplicate positions when one fails. That transaction-policy question is recorded separately as Needs clarification; it is not the failure described here. Saved workspace reopening still fails with existing BUG-001.

All injected faults are disabled. Normal Creator recovery and authorized Admin cleanup restored unique section positions. The Article and Download metadata markers remain in their original sections; the Download markers are metadata-only fixtures with no stored cloud object. No upload, delivery, payment, cloud mutation or application fix occurred.

Deletion flushes nested saves, then saves normalized remaining positions after successful removal. Independent PATCHes are not transactional; partial failures can leave partial server order until retry.
