# BUG-072 — Older Order response closes the currently selected drawer

- Severity: Medium — the valid selected Order disappears without a selection change.
- Status: Confirmed in current-source browser timing test; not fixed.
- Case: SALES-009.
- Environment: actual frontend App/router/store with sanitized copies of two deployed synthetic Order responses and controlled read-only request timing. No deployed latency reproduction or unauthorized disclosure claim.

## Reproduction

1. In the normal Sales ledger, click Order A while its detail request is delayed.
2. Before A returns, click Order B. Let B finish and its drawer open.
3. Release the older A response.

## Expected

The already loaded B drawer remains selected. A response for a previous selection cannot replace current detail state.

## Actual

The B drawer closes, even though the URL still selects B. Reload opens B correctly. A's details are not shown under B: the page checks the returned ID, which prevents wrong-detail rendering, but the overwritten store state leaves no selected drawer.

## Implementation and evidence

`sales.slice.ts` accepts all detail fulfillments without checking the current request/selection. `sales-page.component.tsx` renders the drawer only when `currentOrder.id` matches the query ID. The older A fulfillment therefore overwrites B and makes that guard false.
