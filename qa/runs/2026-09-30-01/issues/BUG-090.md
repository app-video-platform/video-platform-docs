# BUG-090 — Password visibility buttons have no accessible name

- Severity: Low — assistive technology cannot identify the visibility action.
- Status: Confirmed in deployed sign-in and registration forms on 31 October 2026.
- Case: UX-016; related media/icon naming scope UX-018.

## Reproduction and actual result

1. Open `/auth/login` as Guest and use Tab through Email and Password.
2. The next focusable control is an unnamed button before Sign in. It has no text, `aria-label`, `aria-labelledby` or title.
3. With only a dummy value entered, Space changes Password from `password` to `text`; another Space returns it to `password`. The control remains unnamed in both states.
4. On `/auth/signup`, both Password and Confirm Password have the same unnamed focusable visibility controls.

The fields themselves have associated labels. Keyboard activation works; the defect is the missing action name and its failure to describe the current visibility operation.

## Expected and implementation

Each visibility control has a meaningful accessible name that identifies its action. Current PasswordInput passes an eye icon and click handler to shared Input, whose suffix button renders only that icon without an accessible label. The native accessibility tree and button attributes confirm the deployed symptom; no deployed source revision or screen-reader speech is asserted.

No password was changed, no valid registration was submitted and no provider identity was activated. The original synthetic Creator session was restored. No implementation fix was made.

Consolidated evidence: `deployed-contact-and-auth-keyboard-validation-2026-10-31` in the existing browser evidence file, including the two sign-in visibility states and registration keyboard inventory.
