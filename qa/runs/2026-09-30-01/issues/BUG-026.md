# BUG-026 — Concurrent reads remain pending after text refresh success

- Severity: High — queued reads can remain unresolved after successful cookie refresh.
- Case: SEC-008, `local-concurrent-text-refresh-two-waiters-remain-pending`.
- Scope: confirmed local frontend integration defect with an isolated synthetic transport. No deployed authenticated refresh trace was captured.
- Local frontend revision: `12765d4568796f8472124383a221b74d82850c5b`.
- Backend contract source revision: `1b860413436d5f850af0ecc228c5b613ebae4836`. Deployed revisions remain unknown.
- Fixture: three synthetic protected reads; no real cookies, tokens, account or data mutation.

## Reproduction

1. Run the isolated browser harness embedded in the batch evidence. It imports the real shared HTTP client and refresh interceptor, with a local adapter denying real API traffic.
2. Select `mode=text` and click Run concurrent reads.
3. Initial profile, Dashboard and Sales requests return synthetic 401 responses.
4. One refresh resolves 200 with `Refresh successful`, matching the current backend controller response. The synthetic transport then permits all three reads.
5. Observe the initiating profile request retry and fulfill, while the Dashboard and Sales promises remain pending and are never retried.

Expected: successful cookie refresh settles each queued waiter and retries its original read. Actual: only the initiating read completes. The recorded one-second checkpoint shows two pending promises; inspected source establishes that their resolve/reject callbacks were discarded, rather than merely awaiting a slow response.

One text-response reproduction was observed. Controls isolate the response-shape dependency. No backend session rotation, actual expired credential, cookie storage or fresh-login UI was tested by this harness.

## Verified local cause

`src/core/api/interceptors/refresh-token.ts` reads `res.data.token`, then calls `processQueue(null, newToken)`. The queue resolves waiters only when `token` is truthy, and clears the queue afterward. The current backend `AuthController.refresh` returns text, so `newToken` is undefined and queued callbacks are cleared without resolution or rejection. The initiating request is retried separately with `Bearer undefined`; that header is also recorded in the fixture, without any real credential.

A repair should align the cookie-based refresh contract and settle every waiting request on success. No implementation repair is part of this execution pass.
