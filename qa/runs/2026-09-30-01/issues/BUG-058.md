# BUG-058 — A different Creator sees the previous account’s cached reporting data

- Severity: High — account-scoped business data remains visible after a normal account switch.
- Case: JOURNEY-006.
- Environment: unchanged current frontend `12765d4568796f8472124383a221b74d82850c5b`, actual local backend `1b860413436d5f850af0ecc228c5b613ebae4836`, migrated PostgreSQL. Deployed reproduction is not claimed.
- Accounts and data: isolated synthetic Creator A and Creator B. A has one customer and owns Alpha, Shared Collection and the Hidden checkout Course. B has two customers and owns only Beta.

## Reproduction

1. Sign in normally as Creator A. Visit Dashboard, Customers, Sales and Analytics so their real responses are cached.
2. Use the normal account menu to log out. Sign in as Creator B in the same tab, without reloading or closing it.
3. Delay B’s real reporting requests. Inspect Dashboard and the reporting routes while those requests are pending.
4. Release the requests and inspect the same routes again.

Expected: each screen shows B’s data or a loading state. A’s account-scoped data must not appear under B’s authenticated identity.

Actual: the menu and greeting identify Creator B, while Dashboard still shows A’s activity, including the Hidden Product `QA 2026-10-16 checkout response-loss`, A’s Product links and attention count. Customer and Sales filters contain A’s three Product names instead of B’s single Beta Product. Analytics shows A’s one-customer metrics instead of B’s two-customer metrics. B’s own data replaces these values after the real responses arrive.

The local request gate held real GET requests for about 6–13 seconds and then forwarded them unchanged. It did not fabricate responses, change authentication, or initialize application state. The stale observations were captured between each request’s held and released timestamps.

## Evidence and scope

[Existing browser batch](../evidence/browser-populated-reporting-batch-2026-10-03.json), key `normal-account-switch-populated-library-reporting-isolation-2026-10-16`, contains the account fixtures, normal navigation observations, request-gate trace, settled/reloaded results, actual backend scopes and source snapshots.

The backend returns B’s own Product options and customer relationships. B’s attempt to update A’s Product returns 403. User A to User B Library switching shows a loading state and then only B’s entitlement; no access grant transfers through the retained Cart or wishlist. This finding does not establish unauthorized backend data access.

Source inspection explains the visible behavior: logout clears Auth state, while Dashboard, Customers, Sales and Analytics retain their account-scoped Redux values. Pending actions keep those values, and the screens continue rendering cached data when it exists. The root store has no account-change reset for these slices.

Request gates are disabled. Cart and wishlist were cleared through normal controls. Two new synthetic accounts, three Product fixtures and three explicitly created free-enrollment grants are retained locally for future testing. There are 20 Users, four Courses, one existing fake order and three entitlements. Cloud data and the human account were not changed. No fix was made.
